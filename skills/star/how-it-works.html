juel:star · how it works

How STAR Works

You give STAR a brief. STAR asks you only for what a person must supply (a secret, an account, an action at your screen, a required approval, access) and runs everything else itself: it turns the brief into items, has each one explored, makes the product calls from cited sources, and logs them for you to overrule. A build worker per item plans, has gpt-6-luna execute, verifies, and loops through a headless codex gate until its draft PR passes. A babysit worker takes the PR through the hosted review or green CI, and STAR merges it when every gate holds.

Grounded decisions

STAR makes product calls without asking you, so every decision a worker or STAR takes names its source and is a record you can overrule.

What a worker consults

  • A user-facing change: Mobbin for how real apps solve it (screens, flows, sections), together with the frontend-design:frontend-design skill for the visual and interaction choices.
  • A technical question (a library, framework, SDK, API or CLI): Context7, for the version the project uses, else a web search, official docs first.
  • A project convention: the code already in the repo, cited as file:line. A file-name or id form is named only by quoting the check that enforces it; with none, the brief names no form and the build follows the repo.

How it's logged

  • Each decision is a short record in the brief: context, decision, consequences, source.
  • Before deciding, a brief worker searches the decisions already taken, in this project's library and in every approved brief (recall.sh, one line per hit). One that fits is reused and cited; the rest are decided from sources.
  • A decision reused across items, and every call you correct, goes into the library (library/<project>/), so you correct a call once. The digest in the dashboard chat lists reused decisions apart from new ones.
  • When a batch has finished drafting, STAR posts one digest in the dashboard chat: each item, its criteria, the decisions made and the ones reused. No reply is expected and nothing waits on it, so there is no batch summary to approve. Tell STAR what to change on an item and it redoes that brief.
  • A decision with no source is not taken. The worker researches first, or brings STAR sourced options. One no source can settle and only you can make (money, a policy, a legal question) is a person item.
  • STAR picks among the options a worker brings. It does no research in its own session.
  • STAR searches the library before it answers a worker's product call, so a mid-build answer never undoes your correction.
  • A rule STAR sends a worker to keep following (a gate policy, how to log progress) goes into the brief's decisions before it is sent, so a restarted worker keeps it too.
  • STAR records at every start which of Mobbin and context7 its session has, and every worker reads that list. A worker uses one only when its own session has it too; otherwise it searches the web and says so in the record.

Checks at the screen

Workers run every check they can. What needs a person is asked once, as a person item, at any time, and only the item that needs it waits.

Automated, by the build worker

  • Web flows: Playwright, headless, no screen lock.
  • Electron render checks: a hidden dev build driven over CDP, no screen lock (juel:verify's Electron row).
  • Native apps, real browser windows and Electron checks that need the desktop (keystrokes into other apps, OS prompts, packaged builds): computer use through orca computer, one worker at a time under the screen lock.

Asked once, done by you

  • A sign-in with 2FA, SSO or a passkey.
  • A macOS security prompt: keychain, Gatekeeper, a privacy permission. macOS refuses synthetic clicks on these.
  • Touch ID, or a CAPTCHA.
  • A prompt only the new code triggers is planned around up front: a test account or a keychain entry approved ahead.
  • A step you can't do now: that item waits, the rest keep moving. Your answer goes into STAR's notes, so the same question never comes back.

Computer use needs Orca's Accessibility and Screen Recording permissions on each machine, allowed once, as a person item.

Merge gate

STAR merges when every gate holds on the final head commit, per project. merge.sh posts Merging head <sha>: codex PASS, required checks green[, <reviewer> passed]. on the PR, then runs gh pr merge --match-head-commit <sha>, so GitHub refuses if the head moved. No admin bypass, ever.

Always

  • Codex PASS posted on the PR for that head, with a VERDICT: PASS line: gated on that head, or carried to it from a gated head by a base merge that changed none of the files the branch changes. A gate round run on that head later still posts its own PASS: a direct verdict supersedes a carry
  • Every check SUCCESS, NEUTRAL or SKIPPED
  • Every check the branch rules require has reported on that head: one still missing waits, and a merge GitHub refuses for it is tried again, never counted as a failure
  • A written disposition for every unfixed finding
  • GitHub reports it mergeable, so branch rules still apply
  • A reply from the author on every unresolved review thread someone else opened
  • One merge per base branch at a time: a PR with no hosted pass left goes first, then the oldest, and the others sync with the new base in the same tick

Hosted reviewer set and not paused (Greptile)

  • Before READY, the babysit worker judges Greptile's review from guidelines: it reviewed the head commit, scores 4/5 or better, and has no open P0/P1 and nothing advising against merging
  • The merge gate reads no review text: it trusts that READY came on a head the worker judged clean
  • A hosted reviewer that is down is waited on, never merged past: it is that project's own bar
  • At most 2 passes: one when marked ready, one on the single fix push (automatic with triggerOnUpdates, else an @greptileai comment). When the record of passes is missing, babysit rebuilds it from the PR's reviews and Greptile's summary comments first, so a pass already made still counts. One pass per head: a second run on a head already reviewed is a refresh, never a pass, and the build never pings Greptile, since marking the PR ready starts its run
  • Pass 2 still not clean: back to STAR to re-scope
  • A base sync after a clean pass gets one status refresh (@greptileai) on the new head; it is not a pass, unless the project counts every run (refreshOutsideCap: false): then that head comes to you
  • When one pass is left, babysit merges the base in before asking for it, so the last pass reviews a current head

None, or paused

  • Green required checks plus the codex PASS merge it
  • No second approval, unless branch protection requires one: then the row waits on a person item of kind approval ("approve PR #n"), because only a person can meet a GitHub rule. The PR author's own approval doesn't count, and agent approvals never do

Per project

  • mergeMethod: merge, squash, rebase, or the first the repository allows. A method the repository forbids is a person item of kind access
  • baseBranch is where every STAR PR goes. ownerBranches lists branches only you merge into: STAR never opens a PR into one or merges into one. sphere-os-browser merges to dev and you do dev to main. An item whose whole point is a merge into an owner branch is set aside with a note, and nobody is asked
  • A red check that is not required passes only on a red-check-proof the gate confirms with gh (the base fails the same check, an infrastructure failure, or a rerun passes), and STAR files a follow-up after the merge, once per check and base branch. A PR's own red check is never merged

Where you are needed

Only for person items, shown in one combined Needs you across every project on the dashboard. Each is asked once.

  1. Give the brief: free text, tickets, or both. Feedback you give while an item's brief is still drafting lands in that brief.
  2. Do a person item when one is asked: a secret, an account, an action at your screen, a required approval or access. A step that asks for a value (a host name, an id) takes your answer as that value. A step you turn down in words goes back to the brief worker, which plans without it.
  3. On a project whose branch protection requires an approving review, approve the PR when its approval item asks.
  4. When gh cannot see a repository: set tokenCmd in star.json once (a keychain lookup). Every session in the project then gets the token. With no tokenCmd, every worker acts as the same GitHub account STAR does. STAR's own scripts use that account too, whatever account the keyring has active.
  5. On a set-aside item, answer try again or drop. It is a note, never a question: nothing waits on it.

Any time: read the decision records in each brief and overrule a call, by telling STAR what to change on that item.

A hold you give with a date waits on its own, without asking again.

When the review gate is down on every model, nobody is asked: STAR parks builds and babysits and checks it every 30 minutes.

A report item's report is posted to its ticket without an accept step. A sort-memory-notes report ends with a message in the dashboard chat saying where its proposal is and how to apply it; STAR never applies it unread, and until you do, workers read the old notes file.

Open STAR's folder in Obsidian as a vault for tables of the decisions and notes in force (library.base, notes.base). Nothing in STAR needs Obsidian.

On Claude Code 2.1.287 and later, a band above STAR's prompt shows the pools and what needs you, three items at a time, and you answer them right there: click the reply field (Claude Code's fullscreen layout; elsewhere press ctrl+x tab), type, Enter. With cswap installed it also shows each account's usage and the one in use, and starts cswap auto for STAR's Claude login when it is off. juel's mod also holds STAR to its rules: a direct gh pr merge is refused in STAR's session and its workers, and so is reading a review, evidence, report or log file into STAR's session.

/juel:star dashboard opens one local page for every STAR project on this Mac: what needs you, answered right there, each item's progress, the evidence of what merged, and search. When STAR has a pick on something it asks you, it marks the option it recommends and says why in one line, never for a secret. A Slack message the dashboard routes to a project comes to you with a reply its drafter (Opus 5.5, read-only) already wrote in your voice from the project's code, briefs and PRs: send it, have it rewritten, or skip it. STAR never writes reply text. Only a direct message, a mention of you, or a message that asks you for something gets one. Run it again and it opens the page of the server already running; it replaces only a server another checkout started. A Slack reply is marked sent only once it has posted. STAR raises each Slack message once, even when the dashboard hands it over again.

The dashboard's Chat page talks to the running STAR: your message reaches STAR's inbox, and it answers in the thread within seconds, acting only through its own rules, and it asks you only for what a person must supply. Its away switch does what /juel:star away and back do, and STAR posts what still needs you into the chat. Its Accounts page shows your cswap accounts, read-only, and from a phone you reach it over your tailnet: /juel:star dashboard --tailnet maps it with tailscale serve, never tailscale funnel, and prints the link; the server itself stays on 127.0.0.1.

Never stalls

  • Every failing step spends one try from a budget in star.json: tries.perStep (3) per step, tries.rescopes (1) and tries.followUpDepth (2).
  • A quality failure (a NOT-SAFE gate round, red CI, a hosted review with blocking findings, a conflict) is re-scoped once after its tries are spent: the part that works ships, the rest becomes a follow-up. An infrastructure failure (a stage that could not start, a lost worker, a down executor) runs the stage again, then sets the item aside, since shrinking it fixes nothing.
  • Set-aside is a note in the queue with try again or drop, never a question. Nothing waits on it, STAR keeps working on everything else, and try again gives fresh tries.
  • A follow-up is filed in the tracker (or as a spec file) and picked up by STAR itself, with no approval. One past tries.followUpDepth is filed but set aside, so follow-ups never breed forever.
  • A base sync, and a wait on something outside STAR (the hosted reviewer, CI that has not reported, the host gate, the codex gate being down), spend no try.
  • Workers are judged by progress: their progress log, their latest commit and the files changed in their worktree. Each tick STAR also reads the step a worker is on and the PR itself, sends a concrete instruction when the step stalls, and restarts the stage on its own when the evidence is plain or two instructions go unanswered. A stage that has used its tries is set aside.
  • Capacity and 503 errors retry with backoff, then move to a fallback model, then the session runs the plan itself. The codex gate retries Sol, then runs the same review on Claude. With both down, STAR parks builds and babysits, asks nobody, and checks the gate every 30 minutes until it is back.
  • A worker stalled on a model at capacity, or left at an empty prompt under an API Error: line (a connection lost or a server error mid-response), gets up to three retry nudges in one silent stretch, shared by both; the API error nudge also tells it to check a background command it started before starting it again. Then the stage restarts once, and a stage that stalls again spends a try like any other failure. A progress line comes only from the step it names, never from a timer the worker left running, and the probe reads the screen before the progress log, so a stalled worker does not read as moving.
  • A codex gate still NOT SAFE after 3 rounds in a row, or a second Greptile pass still not clean, goes back to STAR, which re-scopes and builds again. In babysit the count starts over at each SAFE round and each push, so a base merge after a SAFE round gets a fresh budget.
  • After round 1, a codex round reviews the commits since the last round and checks that round's findings: a defect in code an earlier round already reviewed is a P2 there, and a P0 still blocks anywhere. A SAFE round's P2 and P3 findings get no push of their own.
  • A re-scope that only narrows the brief, with no new code to write, goes straight back to the codex gate on the same head.
  • STAR waits for worker messages in the background, one wait at a time, so a chat message, a nudge or your own words reach it within seconds. The wait's 9-minute limit is still the clock, a wait that died is replaced on the next tick, and an idle STAR starts none.
  • STAR answers a worker's in-scope question at once, product calls included, from the sourced options the worker brings.
  • Workers read only the notes that apply: a brief copies the ones for its item, and every worker reads the short set marked always. A note you change replaces the old one, and nothing is deleted.
  • A finished worktree's spec and plan are kept beside its evidence, and dependency and build folders are left out of evidence and listed.
  • Evidence keeps proof, not inputs: packages, models, build output, git objects and audio over 10 MB are left out too, duplicates are hardlinked, a superseded run keeps only its text, and a finished item's codex transcripts are compressed.
  • A worker sitting on a prompt is seen on its screen. STAR answers Claude Code's safety prompt for an rm inside the item's worktree or a scratchpad, and any other prompt comes to you.
  • A hosted review that reviewed nothing (a usage limit) is not a pass: STAR parks every babysit and starts them again after 30 minutes, never merging past the reviewer and asking nobody.
  • A spec file outside the STAR folder is copied into it at ingest, with the files it names, so a scratch folder that goes away takes nothing with it.
  • The codex gate names every site of a finding class in one finding, and each fix covers every site of its pattern in the same round.
  • A criterion only CI can prove is not failed in a codex round while its check has not reported: the merge gate needs every check green on the head. A red check, or a change to the check itself, is still a finding.
  • Plan tasks only a session can run (a live measurement, a screen, a browser profile) run in the build worker's own session, and codex runs the rest.
  • Every codex dispatch names the session task it stops before, so the stop holds even where Codex did not load the executor skill, and a run that completed a session task anyway is a failed run. The executor skill is linked into the Codex home codex exec reads, CODEX_HOME included.
  • A worker that lost its Claude login (an account switch logs every session of the profile out) is not failed and spends no try: one screen person item asks for /login, closes itself once the login is back, and STAR restarts the stage on its own. A login lost on every worker at once is named as an account switch.
  • A codex usage limit runs the plan in the worker's own session, and a worker sitting at a Claude usage-limit screen restarts once instead of failing. A second report from a worker STAR already released changes nothing.
  • A codex gate still NOT SAFE at its cap with every blocking finding in a harness the build marked tooling (graded for safety only) goes on under one follow-up that continues the same PR with a fresh round budget, and the parent closes when the follow-up merges.
  • Away holds nothing: it only limits notifications to what needs you. STAR marks ready, pings reviewers and merges as soon as the gates hold, at any hour.
  • A PR that conflicts with its base while babysit waits is synced at once: base merged in, gated, pushed. A hunk where one side edited a line and the other inserted lines right after it is merged as the edited line, then the inserted lines. A base merge that changed none of the files the branch changes keeps the last codex PASS, so no codex round runs for it. A gate round on a base that moved and changed the branch's own files merges the base in first, so the round reviews a current head. Apart from babysit's sync before READY and STAR's sync after the base moved, a worker merges the base in only when the PR conflicts or a gate round refuses with base-moved. The full regression gate and every live check run once per PR, before the first draft push. Heavy gates take turns on one lock for the whole machine, and a gate that prints nothing for 15 minutes is stopped and reported as stalled, so it never holds every build. Each later push runs the tests for what it changed plus a sweep that runs every test file once, and a live check again only where its runtime code changed; a push that only merges the base runs the sweep, after a clean merge too. A head GitHub ran no CI on, while the PR does not conflict, waits like a check that has not reported and spends a try only after 60 minutes.
  • Before READY, babysit merges the base in only when the base requires up-to-date branches or the PR conflicts. A base merge whose shared files only gained lines on both sides (a test list, a changelog) keeps the last codex PASS too.
  • Before a stage starts again, a gate its stopped worker left holding the lock is stopped and the worker's own terminal is closed (a session Orca reports released with no retained reason is ended; one a person kept is still kept or held), a terminal still printing holds the start, and a merge you order stops the worker still fixing that PR first, so two sessions never work on one item. A previous terminal Orca no longer lists is gone and never holds a start, and a terminal Orca kept after the worker was released, sitting at an empty prompt with the recap of Claude Code as its newest lines, counts as quiet.
